# Security status

**Not ready for end users.** The library cannot discover, pair, provision, persist or securely store identities or pins. Callers must exchange and verify certificate fingerprints by an authenticated out-of-band method on both devices before using it; an unverified discovery record or IP address must never be treated as trust. The requested two-sided SAS pairing, key protection with Android Keystore / Windows platform facilities, fingerprint-change UX, and auto-receive controls are not implemented. A new certificate must require explicit verification; never replace a trusted pin silently. Do not deploy this as a complete secure transfer app.

`PinnedTls` requires a certificate with private key on each side and compares SHA-256 of the complete DER certificate with an explicit 32-byte pin in constant time, per connection, not through a global callback. Mutual TLS is mandatory and plaintext is not accepted by the engine. TLS 1.3 is enabled, with TLS 1.2 fallback for platform compatibility; actual negotiated versions depend on the OS. The pin is the trust anchor; the callback intentionally does not use PKI hostname, expiration, or revocation validation. This makes secure initial verification and pin storage essential. Certificate issuance, expiry policy and private-key lifecycle remain future work. Certificates, names and offered sizes travel inside TLS, but a LAN observer can see network endpoints and traffic volume.

Receiver approval is mandatory through the API for every offer; rejection occurs before file creation or content transmission. The engine never executes files and never trusts MIME. Names are sanitized and existing files are not overwritten. Controls, count, and total size are bounded, but callers must enforce deadlines and concurrency limits and should choose conservative size and free-space policies. A malicious peer can still consume its allowed space or tie up a connection. A malicious sender can make the advertised digest match malicious content; the hash checks transport integrity, not safety.

No telemetry is implemented. There are no Android permissions or firewall modifications because there is no app yet. Future Android work must use the system picker and SAF/MediaStore scoped storage, appropriate network/multicast permissions, and a visible foreground service if background transfer is supported; no broad storage permission is assumed. Windows users should explicitly allow the app on Private networks when prompted; never change firewall rules silently. Discovery can fail on guest/client-isolated networks, VPNs and firewalls; direct reachability on the same LAN is required. The app must be open or otherwise permitted to receive.

## Invitation building block (not connected to a UI or handshake)

`ConnectionInvitation` can encode a unicast IP address, port, server certificate SHA-256 pin and a random 256-bit bearer secret into a URL-safe code. It is deliberately a **long** code, not a six-digit password: a short user-chosen code would require a reviewed PAKE design to resist offline guessing. The entire invitation is sensitive and must be shared privately through an authenticated channel; never put it in discovery, logs, screenshots, or analytics. Anyone holding it can attempt redemption until expiry or use. The in-memory verifier hashes the secret, enforces a lifetime of at most ten minutes, and allows only one successful redemption, including concurrent attempts; restart loses outstanding invitations. It does not rate-limit failures, handle network messages, display consent, establish TLS, authenticate the sender, or persist trust. It is not itself a secure pairing protocol.

For future integration, the sender must pin the receiver's certificate using the code **before** sending the secret over TLS. The receiver must verify and redeem that secret, show an explicit approval for the sender, and establish and persist an authenticated sender certificate pin in platform-secure storage before the existing mutual-pinning transfer engine is used. The sender must consent too. Discovery/IP alone must never authorize access. These handshake steps and their security review remain unimplemented; do not advertise code-based connection as available.
